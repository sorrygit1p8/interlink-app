# 실제 서비스 후속 연결 순서

이번 결과물은 외부 서버를 **연결하지 않은** 연동 준비 소스다. 이 절차는 사용자가 후속 연결을 명시적으로 요청한 뒤 실행한다. 환경 변수 변경만으로 완료되지 않는다. 신규 계정·유료 자원·운영 배포·스토어 제출은 자동 실행하지 않는다.

## 1. 사용자 소유 환경 분리

사용자 소유 Supabase 프로젝트와 웹 호스팅, Expo/EAS 프로젝트, 앱 식별자·도메인을 확정한다. development/staging/production을 분리하고 첫 검증은 격리된 staging 또는 로컬 인스턴스에서 한다. 키는 이름·존재만 확인하고 기존 주입 인증을 재사용한다. 데모 fixture와 DB 테스트 시드는 운영 데이터가 아니다.

로컬 전체 Supabase 환경은 Docker와 호환 Supabase CLI가 필요하다. `supabase/config.toml`에서 기본 포트는 API 54321, DB 54322, Studio 54323, 로컬 메일함 54324다. 로컬 시작 후 마이그레이션을 적용하고 DB 테스트를 실행한다. `supabase db reset`은 데이터를 지우는 명령이므로 **폐기 가능한 로컬 테스트 DB에만** 사용하며 원격 운영 DB에 적용하지 않는다.

## 2. DB·권한 적용

`supabase/migrations`를 파일명 순서로 적용한다. 이미 운영 데이터가 있으면 백업·롤백·영향 검토를 먼저 한다. 스키마뿐 아니라 외래 키·유일성·상태 제약, 검색 인덱스, 테이블 권한, RLS, 고정 search_path, RPC 실행 권한, 작업 큐를 함께 적용한다.

클라이언트 계약은 `interlink_query(operation, payload)` 및 `interlink_command(operation, payload, idempotency_key)`이다. 클라이언트가 직접 테이블에 승인·멤버십·관리자 상태를 쓰는 권한을 부여하지 않는다. 첫 가입자를 자동 관리자로 지정하지 않는다. 운영자는 검증한 Auth 사용자 ID에 대해 DB 역할을 별도로 부여하고 AAL2를 요구한다.

커뮤니티와 초대코드는 운영자가 범위·만료·사용 횟수를 결정한다. 이메일 소유 확인만으로 학생·연령 인증이라고 표시하지 않는다. Auth 계정이 생기는 것과 커뮤니티 데이터 접근 승인은 별개다. 가입 대상·동의·보호자 절차 등 미확정 정책을 해결하기 전 공개 모집을 열지 않는다.

## 3. 인증·메일·딥링크

Supabase Auth에서 이메일 OTP, 코드 길이 6자리, 만료 600초, 재요청 간격 60초 및 제공자 측 rate limit을 검토한다. 코드 기반 화면을 쓰므로 메일 템플릿은 실제 OTP 토큰을 표시해야 한다. SMTP 발송자·도메인 인증·제공자 제한·반송 처리를 사용자 소유 설정으로 등록한다. 로컬 메일함 테스트는 실제 메일 발송 검증이 아니다.

Site URL과 승인된 Redirect URL을 실제 웹 주소 및 `interlink://auth/callback` 등 앱 설정과 맞춘다. deep link scheme, Android intent filter, iOS URL scheme을 네이티브 빌드에서 확인한다. 설정하지 않은 Google/Apple 로그인은 활성화하지 않는다.

운영자 TOTP 추가 인증을 등록하고 AAL1/AAL2 및 일반 사용자 세션을 구분해 실제 운영 API 접근을 검증한다. 서버는 사용자 토큰을 `getUser`로 검증하고 역할은 DB에서 확인한다. 토큰/메일/OTP/개인 메시지를 로그에 남기지 않는다.

## 4. Storage·Realtime

마이그레이션에 정의된 비공개 이미지 버킷과 객체 경로 정책을 적용한다. `image-upload` 함수에서 사용자 확인·바이트/형식/크기 검증을 거쳐 정규화된 이미지만 저장한다. 클라이언트가 임의 사용자 경로에 업로드할 권한을 추가하지 않는다. 허용 웹 Origin을 `EDGE_ALLOWED_ORIGINS`에 등록한다.

실시간 publication/채널 정책은 마이그레이션과 어댑터 구독 방식에 맞춰 적용한다. 이벤트는 변경 신호이고 DB가 원본이다. 접근 철회 후 이전 소켓에 새 데이터가 전달되지 않는지 실제 인증 세션으로 검증한다. 메시지 전체 본문·삭제 전 내용·신고자 정보를 불필요하게 broadcast하지 않는다. 서명 URL은 만료 전 즉시 철회되지 않을 수 있어 짧은 만료·보관 정책을 함께 검토한다.

## 5. 서버 함수 배포

`supabase/functions`의 `image-upload`, `push-worker`, `deletion-worker`를 배포한다. 설정 파일에서 gateway JWT 확인이 꺼진 함수도 **인증 없는 함수가 아니다**. 업로드는 제공자의 사용자 검증, 작업 함수는 `INTERLINK_WORKER_SECRET`의 상수 시간 비교를 수행한다. 배포 후 외부에서 인증 없이 호출해 거절을 확인한다.

서버 전용 `SUPABASE_SERVICE_ROLE_KEY`와 작업 비밀을 안전한 환경 설정으로 주입한다. 키가 포함된 명령·로그를 공유하지 않는다. 함수 URL과 허용 Origin이 staging/production 환경과 일치하는지 확인한다.

## 6. 작업 스케줄·재시도·푸시

작업 처리기 파일과 `supabase`의 스케줄 예시에 따라 주기적인 호출을 등록한다. 처리기 코드를 배포하는 것과 스케줄을 등록하는 것은 별개다. 작업 비밀은 Vault/호스팅 secrets에서 조회하고 스케줄 SQL 본문이나 저장소에 직접 넣지 않는다.

제공된 `supabase/schedules.sql`은 push 처리 1분, deletion 처리 2분, 유지관리 1시간 주기다. 이 스케줄은 현재 원격 환경에 적용하지 않았다. Vault의 함수 기본 URL/작업 비밀을 안전하게 설정한 뒤 별도 적용하고 실제 cron 응답과 작업 상태를 확인한다.

푸시 작업은 티켓 요청뿐 아니라 영수증 확인을 반복 실행해야 한다. 일시 실패의 backoff, 최대 시도, 잠금 만료, 실패한 작업의 운영 재시도를 점검한다. `DeviceNotRegistered` 등 무효 토큰은 비활성화한다. 로그아웃·탈퇴·정지·차단·선호 변경 이후 발송 직전 대상 자격을 다시 확인한다.

사용자 소유 Expo project id 및 Android FCM/iOS APNs 자격·서명을 등록한다. 기기 권한 요청은 실제 연결 모드에서 사용자가 선택할 때만 한다. 데모 진입은 권한·실제 토큰을 요청하지 않는다. 발송 티켓 성공·기기 수신·딥링크 열기는 각각 따로 검증한다.

삭제 작업은 요청 즉시 신규 접근을 제한하고 소유팀 종료/이전, 프로필·멤버십·신청·경험·토큰·파일 및 외부 Auth 계정 정리를 처리한다. Storage/Auth 일부 실패를 주입해 재시도 가능성과 완료 상태의 정확성을 확인한다. 보존 데이터와 기간은 정책·법적 검토 후 확정한다.

Auth 계정이 먼저 삭제되어 `getUser`가 실패한 뒤에도 웹 `GET /api/account`는 기존 **서명된 사용자 access token의 유효기간 내에서** PostgREST의 본인 `account.status`만 확인하는 제한된 경로가 있다. 삭제 요청 쓰기는 계속 실제 사용자 검증을 요구한다. 토큰이 만료되어 상태를 읽을 수 없다는 사실을 삭제 완료로 해석하지 않는다. 운영자는 삭제 요청 ID와 작업 상태로 확인하며 사용자는 지원 절차를 이용한다.

## 7. 앱·웹 연결 모드

`ENVIRONMENT_SETUP.md`와 `.env.example`에 따라 공개 변수와 서버 비밀을 구분해 주입한다. 모바일 `EXPO_PUBLIC_DATA_MODE=supabase`, 웹 `INTERLINK_DATA_MODE=supabase`로 명시적으로 선택한다. staging/production 환경을 별도로 지정한다. 누락된 URL/공개 키는 설정 오류여야 하며 데모로 전환해서는 안 된다.

앱 번들을 새로 생성한다. Expo 공개 변수는 번들에 들어가므로 실행 서버 환경만 변경해서 이미 배포된 앱 값이 바뀐다고 가정하지 않는다. 공개 클라이언트 키는 RLS를 대신하지 않는다. 운영 번들에 서버 비밀·가상 역할 선택 경로가 노출되지 않는지 검사한다.

## 8. 통합·보안·실기기 검증

`INTEGRATION_TEST_PLAN.md`를 실제 A/B/C 세션으로 수행하고 `TEST_REPORT.md`에 별도 증거를 남긴다. 반드시 마지막 자리 동시 승인/수락, 직접 REST/RPC 우회, 기존 소켓 권한 철회, 타인 Storage 접근, 푸시 무효 토큰, 삭제 부분 실패를 포함한다. 관리자 키만 사용한 테스트로 권한 통과를 판단하지 않는다.

Android/iOS 실제 설치, 키보드·안전 영역·큰 글씨·화면 읽기·뒤로가기·백그라운드·오프라인·딥링크를 검증한다. 접근 불가 프로젝트 deep link는 서버에서 재검증한다.

## 9. 운영 배포와 복구

운영 주체·연락처·정책 URL·보관 기간·위탁/이전·신고 대응·백업/복구·요금·가용성·서명·스토어 조건을 확정한다. 실패 작업과 미처리 신고 모니터링 담당자를 정한다. 마이그레이션·함수·앱 버전의 호환성과 복구 순서를 staging에서 연습한다.

이 항목들이 확인된 뒤에만 별도 승인으로 운영 배포와 스토어 제출을 판단한다. 현재 앱 코드·데모·어댑터·SQL 작성 완료 여부와 실제 서비스 운영 가능 판정은 구분한다.
